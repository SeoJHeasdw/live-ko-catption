# 문장 다듬기 분리와 Hy-MT2 7B 비교 — 2026-10-01

대상은 `polish-lane` 브랜치의 0.4.7 (15), 커밋 `1865bb7`(다듬기 분리)과 `03d1735`(7B 프롬프트 형식)입니다. main은 태그 `v0.4.6`으로 고정돼 있고 이 브랜치는 아직 병합하지 않았습니다.

- **다듬기 분리는 효과가 확인됐습니다.** 실제 음성 파일에서 로컬 모델 문장으로 확정된 수가 12/17에서 17/17이 됐고, 실시간 자막 지연은 그대로였습니다.
- **7B는 동작하지만 채택을 권하기에는 품질이 엇갈립니다.** 문장 구조와 자연스러움은 1.8B보다 나은 경우가 많았지만, 공개 예문에서 정밀도·재현율 정의를 뒤바꾸고 중앙값을 평균으로 옮겼습니다. 문장당 시간은 약 3배, 메모리는 약 5GB입니다. 앱이 설치·사용하는 모델은 계속 1.8B 하나입니다.

실제 마이크, 화면 표시, 팬 소음은 측정하지 않았습니다. 의미 검토는 기준 설명과 출력을 대조해 읽은 결과이며 점수가 아닙니다.

## 다듬기 분리

이전에는 다듬기가 실시간 번역 작업자 안에서 실행됐습니다. 다음 문장의 초안이 대기 중이면 건너뛰고, 새 초안이 오면 취소했습니다.

- 확정 원문의 빠른 번역을 회색으로 표시한 뒤 별도 작업 줄에 넘깁니다. 실시간 번역 작업자는 다듬기를 기다리지 않습니다.
- 새 초안과 새 확정 원문은 진행 중인 다듬기를 취소하지 않습니다.
- 다듬기는 한 번에 하나만 실행합니다. 대기는 2문장까지이며, 넘치면 가장 오래 기다린 문장을 빠른 번역으로 확정합니다.
- 로컬 엔진을 쓰는 문맥 묶음과 다듬기는 동시에 실행하지 않습니다.
- 정지할 때 남은 다듬기를 마친 뒤 마지막 문맥 묶음을 한 번 더 처리합니다. 중단·시간 초과·새 대화에서는 표시 중인 빠른 번역으로 확정합니다.

### 실제 음성 파일

사용자가 제공한 81.6초 영어 음성 파일 하나를 `BidirectionalPolishPipelineChecks`와 같은 경로(실제 로컬 인식 → 제품 `CaptionModel` → 실제 Apple 번역 → 실제 로컬 모델)에 100ms씩 시간대로 공급했습니다. 분야는 IT, 문맥 번역은 켠 상태입니다. 파일과 인식·번역 내용은 사용자 자료이므로 저장소에 넣지 않았고 수치만 남깁니다.

| 관측 | v0.4.6 + 1.8B | 분리 + 1.8B | 분리 + 7B |
|---|---:|---:|---:|
| 확정 문장 | 17 | 17 | 17 |
| 로컬 모델 문장으로 확정 | 12 | 17 | 17 |
| 문장당 다듬기 시간, 중앙값 / 최대 | 239 / 349ms | 230 / 349ms | 687 / 1041ms |
| 문장이 확정 표시되기까지, 중앙값 / 상위 10% | 1.21 / 1.90초 | 1.42 / 1.89초 | 1.62 / 2.12초 |
| 현재 원문과 일치하는 자막의 지연, 중앙값 | 0.14초 | 0.14초 | 0.14초 |
| 누락 입력 버퍼 | 0 | 0 | 0 |
| 이번 실행의 다듬기 중단 알림 | 없음 | 없음 | 없음 |

"확정 표시되기까지"는 음성 구간 끝에서 진한 글씨가 될 때까지입니다. 분리 후에는 건너뛰던 문장도 다듬기를 기다리므로 중앙값이 0.2초 늘었습니다. 그동안 빠른 번역은 회색으로 계속 보입니다. 문맥 묶음 호출은 세 실행 모두 다음 발화에 양보해 취소됐습니다(9·9·8회). 실행마다 인식기의 문장 분할이 조금씩 달랐습니다. 각 조건 한 번씩의 결과입니다.

## Hy-MT2 7B 비교

- 모델: 공식 `tencent/Hy-MT2-7B-GGUF`, `Hy-MT2-7B-Q4_K_M.gguf`, 4,624,648,896 bytes, Apache-2.0.
- 고정 revision: `ab8472660ac61fac25f1af43fac2599d52a8a775`.
- SHA-256: `9f96256500f3fc1ab4d64336b58f52a949a95ad7516b0c229476eef782f9f77b`. 내려받은 파일의 크기와 SHA-256을 직접 확인했습니다. 파일은 Git에서 제외되는 `.build/experiments/models/`에 있습니다.
- 7B는 채팅 템플릿의 제어 토큰이 1.8B와 다릅니다(`<|startoftext|>…<|extra_0|>`). 각 모델의 공식 `chat_template.jinja`에 맞춰 감싸는 형식만 바꾸고 번역 지시문은 같게 뒀습니다.
- 두 모델 모두 기존 런타임의 greedy 디코딩을 썼습니다. 배포처가 권장하는 샘플링 설정(temperature 0.7 등)과는 다릅니다.
- 1.8B는 Q6_K, 7B는 Q4_K_M입니다. 양자화 수준이 달라 모델 크기만의 차이로 해석할 수 없습니다. 7B Q6_K(6.16GB)는 실행하지 않았습니다.

### 시간

네이티브 번역 시간이며 자막 전체 지연이 아닙니다. 예문 수가 적어 최대값은 성능 보장이 아닙니다.

| 실행 | 예문 | 1.8B 중앙값 / 최대 | 7B 중앙값 / 최대 |
|---|---:|---:|---:|
| 영어→한국어 단일 문장 | 12 | 209 / 386ms | 643 / 1503ms |
| 한국어→영어 단일 문장 | 12 | 139 / 227ms | 315 / 608ms |
| 영어→한국어 2~4문장 묶음 | 4 | 380 / 496ms | 1134 / 1918ms |
| 한국어→영어 2~4문장 묶음 | 4 | 247 / 355ms | 621 / 996ms |

토큰당 생성 시간은 1.8B 6.2ms, 7B 14.8ms였고 첫 토큰은 중앙값 29ms와 99ms였습니다. 7B는 영어→한국어 단일 문장 1개와 묶음 1개가 제품의 네이티브 제한 1.5초를 넘었습니다. 지금 제한을 그대로 두면 긴 문맥 묶음에서 시간 초과가 나고, 그 실행의 문맥 보정이 중단됩니다.

5분 반복 실행(2초 간격, 145회, 제한 3초)에서 시간 초과는 0회, 중앙값 573ms, 상위 5% 1039ms, 최대 1367ms였습니다. 프로세스 메모리는 4.98GB로 일정했고 OS 발열 상태는 계속 `nominal`이었습니다. 팬 회전수와 소음은 재지 않았습니다. 기존 QA에서 1.8B의 메모리는 약 1.7GB였습니다.

### 의미 검토: 영어→한국어

| 예문 | 1.8B | 7B |
|---|---|---|
| date-time-zone | **실패:** 일정 요청을 `잡았습니다`라는 완료 사실로 바꿈 | 요청으로 유지 (`예약하세요`). 표현은 어색함 |
| piece-of-cake | 원문에 없는 `파일들`을 붙임 | 쉽다는 뜻과 선행 조건을 보존 |
| deployment-rollback | `복구` | `롤백`, 데이터베이스 보존 유지 |
| 피구·몸 숙이기 묶음 | **문제:** `던지볼`, `몸을 숨기는` | 동작은 `몸을 숙이는`으로 맞음. 종목은 `도드볼`로 음차 |
| precision-recall | 정밀도의 분모는 맞음. 재현율은 원문처럼 수로 표현 | **실패:** 정밀도를 `실제로 악성인 요청들 중에서 … 올바르게 식별`로 옮겨 재현율의 정의가 됨 |
| 분류기 3문장 묶음 | 정밀도는 맞음. **실패:** 재현율을 `다시 감지된 메시지의 비율`로 바꿈 | **실패:** 정밀도와 재현율의 분모를 서로 뒤바꿈 |
| percentages-latency | 수치·중앙값 보존 | **실패:** `median`을 `평균`으로 옮김. 수치는 보존 |
| bank-context (문맥 없음) | `은행가에서` | `강가에서`. 문맥을 주지 않은 예문이라 어느 쪽도 오류로 세지 않음 |
| 그 밖의 8개 | 의미 보존 | 의미 보존 |

숫자·형식 가드는 두 모델의 40개 출력을 모두 통과시켰습니다. 위 실패들은 가드로 걸러지지 않습니다.

### 의미 검토: 한국어→영어

7B가 대체로 더 자연스러웠고 실패가 적었습니다. `Please schedule…`로 요청을 유지했고, 분류기 묶음에서 두 지표의 분모를 구분했으며, `bent her body` 대신 `duck`을 썼습니다. 반면 `충돌`을 `conflicts`로 옮겼고(1.8B는 `crashes`), 피구는 두 모델 모두 다른 종목으로 바꿨습니다(1.8B `baseball`, 7B `pickleball`).

### 실제 음성 파일의 인상

같은 81.6초 파일에서 두 모델의 확정 문장을 나란히 읽었습니다. 7B가 뜻을 더 정확히 옮긴 문장이 4개(제품 이름 보존, 선후 관계, 명령문의 대상 등), 1.8B가 더 정확한 문장이 1개였고 나머지는 비슷했습니다. 내용은 사용자 자료라 싣지 않습니다. 한 사람이 아닌 도구가 읽은 인상이므로 사용자의 직접 확인이 필요합니다.

### 판단

7B는 분리된 작업 줄에서 실제 속도를 따라왔고 메모리·발열 상태도 이 Mac에서 문제없었습니다. 그러나 IT 분야에서 중요한 정의·통계 용어를 확신 있게 틀린 경우가 있어, 지금 자료로는 1.8B보다 항상 낫다고 할 수 없습니다. 앱에 모델 선택을 넣는 작업은 하지 않았습니다. 넣는다면 두 번째 모델의 manifest·다운로드·검증, 모델 선택 설정, 7B에 맞는 시간 제한이 필요합니다.

## 7B Q6_K 후속 확인

Q4_K_M에서 나온 정의·통계 오류가 양자화 때문인지 보려고 같은 revision의 `HY-MT2-7B-Q6_K.gguf`(6,164,482,720 bytes, SHA-256 `88ef0aba59952a4cfe4be36cb5baf797dbb370bc60e9dcbd7297036021e52831`, 크기와 SHA-256 확인)로 같은 예문을 다시 실행했습니다.

| 영어→한국어 | 7B Q4_K_M | 7B Q6_K |
|---|---:|---:|
| 단일 문장 12개, 중앙값 / 최대 | 643 / 1503ms | 777 / 1855ms |
| 2~4문장 묶음 4개, 중앙값 / 최대 | 1134 / 1918ms | 1434 / 2384ms |
| 토큰당 생성 시간 | 14.8ms | 19.0ms |
| 1.5초를 넘은 예문 | 2 | 3 |

- precision-recall, 분류기 3문장 묶음, percentages-latency의 세 실패가 Q6_K에서도 같은 내용으로 나왔습니다. 정밀도·재현율의 분모를 뒤바꾸고 `median`을 `평균`으로 옮겼습니다. 양자화가 원인이 아닙니다.
- 달라진 것은 date-time-zone의 표현뿐입니다(`리뷰 일정을 잡아주세요`).
- 그래서 7B를 앱의 선택 모델로 넣지 않았습니다. 앱의 모델은 1.8B Q6_K 하나입니다.

## 재현

```sh
./scripts/check-app-model.sh
./scripts/check-bidirectional-polish-pipeline.sh /tmp/polish-lane-pipeline.json
./scripts/check-local-polish.sh \
  --model .build/experiments/models/Hy-MT2-7B-Q4_K_M.gguf \
  --runtime .build/local-runtime/libcaption_local_translation.dylib \
  --fixtures Tests/LocalPolishChecks/fixtures.json \
  --manifest /path/to/7b-manifest.json --timeout-ms 6000 \
  --output /tmp/local-polish-7b.json
```

`--manifest`에는 `model`, `quantization`, `repository`, `revision`, `filename`, `byteCount`를 담은 JSON을 줍니다. 생략하면 앱의 1.8B manifest를 읽습니다. `--soak-seconds 300 --soak-timeout-ms 3000`을 더하면 반복 실행을 합니다. 실제 음성 파일 비교는 같은 통합 검사 실행 파일에 비공개 fixture를 준 것이며 저장소에는 넣지 않았습니다.
